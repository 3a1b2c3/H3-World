# 从"动作控不住"到逐 latent 文本注入：方案、踩过的坑、怎么修的

> 这篇记录做这件事的过程本身：每次方案怎么定的、撞上什么问题、怎么定位、怎么修。
> 只想知道当前方案是什么，看 [`pipeline_text_injection.md`](pipeline_text_injection.md)；
> 想看设计推导，看 [`action_text_injection_plan.html`](action_text_injection_plan.html)。

目标：让 MiniMax-H3 的生成受按键控制 —— 同一个首帧、不同的按键序列，
应当生成出不同且符合指令的画面运动。终点是流式续写 + 动作可控的世界模型。

---

## 一、两次失败，和它们教给我们的事

### 第一次：加性 bias

把 8 维按键嵌入成向量，加在每个 DiT block 的入口：`x + emb(a)`。训完 2952 步，
推理出来像在胡乱操控。诊断不是"训练不够"：

| step | 单层 bias L2 | 相对 hidden(224.55) |
|---:|---:|---:|
| 500 | 0.0947 | 0.042% |
| 1500 | 0.1796 | 0.080% |
| 2500 | 0.2396 | 0.107% |

增速持续衰减，训完也到不了有效区间。真正的根因在梯度：

```
每步实际更新 / Adam 理论步长    1.92%
ΔW 与已有 W 的方向余弦          +0.064   （几乎正交）
|W₅₀₀| + |ΔW| = 3.93           实际 |W₁₀₀₀| 只有 2.87   -> 明显抵消
```

**表达能力上的硬伤**：`Δx = b(a)` 与画面内容无关。但"按 D 键"的视觉效果依赖当前朝向
和场景 —— 面朝东按 D 和面朝北按 D，画面变化完全不同。不同样本要求 `b` 指向不同方向，
平均下来就抵消了。调学习率只会让一个方向错误的量长得更快。

### 第二次：FiLM

换成 norm+AdaLN 之后的 per-latent-token 乘性调制：`h·(1+s(a)) + sh(a)`。
乘性 = 内容相关，理论上正好治上面那个缺陷。跑到 3000 步：

| 区间 | 平均 \|scale\| | ΔW·W 余弦 |
|---|---:|---:|
| 500→1000 | 0.183% | +0.122 |
| 1500→2000 | 0.267% | +0.093 |
| 2500→3000 | 0.330% | **+0.047** |

量级涨了 3 倍，**方向余弦反而掉到比 bias 基线还低**。

### 结论

两种机制不同的注入方式给出同一个失效签名。这说明问题不在"乘性还是加性"，
而在**信号本身** —— 8 维按键没有携带足够信息去解释画面该怎么变，
所以不同样本仍在要求相互矛盾的更新。

> **方法论上的收获**：这两次都是靠**权重差分**判死的，不是靠看视频。
> `compare_action_ckpt.py` 两个 checkpoint 一比就出结论，几分钟；
> 而渲一条视频要 8 分钟且只能给出"像不像"的主观判断。
> 后面每换一个方案，第一件事都是先把判据做出来。

## 二、转向：从"怎么注入"到"注入什么"

调研了 20 种注入方式（[`injection_options.html`](injection_options.html)），
过程中撞上两个自己的判断错误，都值得记下来。

### 错误一：以为 H3 没有 cross-attention 就接不了外部条件

我最初把"文本接口"判为"范式不符"。查代码才发现 H3 的序列布局是：

```
[text | cond | audio | video | pad]
```

**文本本来就是同一条 self-attention 序列里的一段 token。** H3 没有 cross-attention
不是因为它不能接外部条件，是因为它用拼接解决了。所以"用文本注入动作"根本不是被
架构排除的方案，而是走它**预训练过的**那条通路。

### 错误二：读论文摘要下结论，没看代码

Incantation（arXiv:2605.18601）做的正是逐帧语言条件。论文摘要说它"在双向骨干上
微调"，我据此推翻了自己原来"依赖自回归"的判断。**拉下源码才发现原判断是对的**：

```python
for fi in range(num_gen_frames):
    context = prompt_embeds_list[fi]      # 只有这一帧的 prompt 在 context 里
    noisy   = torch.randn(1, C, 1, H, W)  # 一次只生成 1 个 latent 帧
```

它的逐帧绑定**来自逐帧生成本身**，不是任何掩码技巧；那个 `cross_attn_mask` 只是
防止文本污染 KV cache。摘要里的"双向"指的是 Wan2.2 预训练权重的出身，不是训练时的
注意力结构。

> **教训**：涉及机制的判断，论文摘要不够，要看代码。这次是拉了源码才没走错路。

### 定下来的方案

条件走文本通路，每个 latent 一条结构化文本，由 **9 位按键的纯函数**生成：

```
the man <怎么动>, camera <相机视角怎么动>
```

三条支撑：**条件通路零新增可训练参数**（前两次的病灶不存在）；
**硬绑定靠掩码**（自注意力对 token 置换等变，光塞进序列模型不知道哪条对哪帧）；
**第 9 位 `F` 由 COLMAP 实测速率合成**（方向能从按键读出，速度读不出来，
这一位是唯一真正超出原始 8 bit 的信息）。

## 三、先验证信号，再动模型

方案定了不急着改代码，先花十几分钟回答一个问题：**H3 的文本通道到底控不控运动？**

拿基座模型（零训练），同首帧同 seed，只改 prompt 尾句。判据不靠肉眼 ——
用相位相关估每帧的全局水平位移。先标定符号：

```
cum_dx 与 npy 的 Σd_yaw：相关系数 r = -0.936，14/14 反号
-> cum_dx 为负 = 相机左摇
```

结果（三条样本）：**2/3 强阳性**。

> **中途改错的判据**：第一版用"left 与 right 的累计位移符号相反"作为方向性测试，
> 结果全是"符号相同"。**片段本身有固有运动，基线不是零** —— 应该看相对 `none` 基线
> 的偏移。改过来之后：`left` 相对基线 −102（更向左）、`right` +14（更向右），
> 方向全对、幅度单调、效应量 2.53× 空对照。

顺带推翻了自己的一个预测。我说过"CFG 该等训练后再测，因为需要先训 dropout"。
实验否掉了：

| 条件 | `right` 相对基线 |
|---|---:|
| cfg=1，空负 prompt | +14 |
| cfg=5，空负 prompt | +2 |
| **cfg=5，动作零参考负 prompt** | **+131** |

我把"负 prompt"和"模型学到的无条件分布"混为一谈了。dropout 训练是为了得到一个
**学出来的**无条件参照；而这里的负 prompt 是**显式写出来的**动作零参考文本，
CFG 只是在两段文本的输出之间做外推，不需要模型学过什么。

## 四、规则表：四个 bug 都是打印真实例子才暴露的

规则表的自检（词表统计、覆盖度）**全是绿的**，看不出任何问题。真正的错误是把三条
真实片段的 37 行标注逐行打出来才发现的。

**① 相机从句漏读了 3 个平移通道。** 看到 27 步连续 `strafes right, camera holds steady`，
怀疑 COLMAP 掉点，查全部 6 个通道才发现 `d_x_right = 0.98` 非零 —— 第三人称跟随相机
只平移不转动是常态。我只读了 `d_yaw`/`d_pitch`。

*全数据集量化：**23% 的标注写着"相机静止"但相机在平移**。* 这不是数值噪声，
是字面写错的事实陈述。改成三态：旋转显著→摇镜；旋转近零但平移显著→`follows him`
（角色也在动）或 `drifts <方向>`（角色没动，才是新信息）；都近零→`holds steady`。
假 steady 从 0.234 降到 **0**。

**② `sharply/slowly` 分档是分箱假象。** 修完 ① 后标注开始 A-B-A 抖动。查发现低值全落在
k=0,5,10,15…，正是 `_FRAME_PER_TOKEN=(1,4,4,4,4)` 里那些只覆盖 1 帧的 bin ——
相机通道逐帧求和，1 帧 bin 天然只有 4 帧 bin 的 1/4。**8/37 = 22% 的步被误判成
"相机变慢了"，其实是 bin 变窄了。** 判档前除以 bin 帧数换算成逐帧速率即可。

**③ 窄 bin 方差偏高。** ② 修完，1 帧 bin 的 `holds steady` 出现率仍比 4 帧 bin 高 0.127。
这不再是尺度问题 —— 单帧只测 41 ms，估计天生更抖。标注要描述的是该 latent 所处的
运动状态，不是 41 ms 的瞬时采样，所以让窄 bin 借邻居凑够窗口再估速率。
偏差 **0.127 → 0.003**，孤立抖动 0.039 → 0.013。

**④ 矛盾的移动组合。** `walks forward and walks backward and strafes left and strafes right`
—— `bin_to_latent` 对按键取 `amax`，4 帧窗口里先按 W 后按 S 会让两位同时为 1。
对轴相消（W∧S、A∧D）后词表 116 → 98。

**⑤ I/K 符号写反。** 实测 `K` 的 `d_pitch` 均值 +0.131（95% 为正 → `tilts up`），
`I` 是 −0.123。降级路径里我写反了。

> **教训**：统计量能验"分布合不合理"，验不了"这句话跟画面对不对得上"。
> 后来专门做了[标注核对台](action_prompt_viz.html)：播放视频，当前 latent 的按键与
> 标注同步高亮，用来肉眼核。

## 五、9 位按键：为什么多一位

`sharply/slowly` 这一维从按键里恢复不出来，实测三条：

| 问题 | 结果 | 结论 |
|---|---|---|
| 按 J 的步里 slowly / sharply | 0.66 / 0.34 | 接近抛硬币 |
| 速度随按住时长变化？ | 第 0 步 0.122 → 第 1–5 步 0.203 → 第 6 步+ 0.176 | 第 0 步偏低只是分箱边界效应，之后即平台 |
| 速度是片段级常量？ | ICC ≈ 0.475，整段档位一致仅 38.9% | 都不是 |

三个选择：

```
A  去掉速度档，4 键          查表准确率 0.890   但相机从句退化成 IJKL 的确定性函数
B  保留速度档，4 键          查表准确率 0.700   30% 的错全来自速度猜不中
C  4 键 + 一个 fast 修饰键    查表准确率 0.871   多一个 bit
```

选 C。A 准确率最高，但它把 COLMAP 那 6 个通道测出来的信息全扔了 ——
方案又回到"把 one-hot 换成英文，信息量一个比特没多"。

改成 9 位纯函数之后还有一个额外好处：**训练与推理走完全同一条路径**，
不会出现"训练用连续量、推理用离散键"的表示失配。词表 98 → 60。

## 六、工程上的坑

### 数据构建：训练/推理不一致，且损坏了 2400 条

注入脚本原本**沿用缓存里已有的图像 pad 行**（那是首帧过视觉塔、并与旧场景描述一同
编码的产物）。做推理侧对接时才意识到：推理时没有这些缓存行，得重新走一次
`presentation_fl2va`，两边头部来源就不同了。

更糟的是，已改写的 2400 条**把场景描述行覆盖掉了**，缓存里恢复不出来。

改法：**头部每次从源数据重新编码**，走与推理侧同一次调用。三重好处 ——
训练/推理由构造保证一致、被损坏的条目自动修复、幂等性只取决于源数据。
实测 0.25 s/条，8 卡分片 4 分钟，代价可忽略。

### 掩码：一个静默数据损坏级的 bug

第一次起训崩在 `FailOnRecompileLimitHit`。表面看是 Dynamo 重编译上限 ——
`flex_attention` 是 `torch.compile` 过的，每个不同的序列长度触发一次重编译，
而逐条样本的 `text_len` 不同。推理时没暴露，因为只有一条样本、一个形状。

顺着查下去发现根因严重得多。做了个顺序对调实验：

```
顺序 A：先无 pad 后有 pad     无 pad 5.07e-07 ✓    有 pad 3.02e+00 ✗
顺序 B：先有 pad 后无 pad     有 pad 5.07e-07 ✓    无 pad 3.02e+00 ✗
```

**先跑的对，后跑的错，与掩码内容无关。** `mask_mod` 闭包被内联进编译后的 kernel，
第一次调用把它烘焙进去、之后复用。放到训练里就是：

> **第一条样本之后的每一条都用着第一条的掩码，全程不报错，
> 只会训出一个学不到绑定的模型。**

我原来每条样本都新建闭包（捕获 per-sample 的张量和 `lim` 整数），同时造成两个后果：
Dynamo 判定新图 → 撞重编译上限（**这个报错了**）；kernel 复用旧闭包 → 掩码错乱
（**这个不报错**）。

**修法**：`mask_mod` 永远闭在同一批**持久缓冲区**上，按 `(device, 段起点, 段长)` 复用，
per-sample 数据原地写入；`lim` 从 Python int 改成 0 维张量（否则被当常量烘焙）。
配套把有效长度 padding 到全数据集统一值，序列形状恒定、只编译一次；补出来的零行
必须屏蔽 —— 不屏蔽会参与 softmax 改变分母，且 pad 行只允许看自己，否则整行无可见
key、softmax 出 NaN。

**探针加了两条判据固化这个教训**：

```
[5] padding 行被正确屏蔽
[6] 连续 5 个不同掩码全部正确    <- 专门抓这类静默损坏
```

### 起训崩在第 0 步：autotune 把 CUDA context 弄脏了

数据建完、8 条判据 7872/7872 全过，起训在**第 0 步**就挂了。8 张卡里只有 **rank2** 死，
其余 7 张是被 SIGTERM 连坐。报错分两层：

```
No valid triton configs. OutOfMemoryError: triton_flex_attention
  Required: 233472   Hardware limit: 232448        <- H200 共享内存，差 1 KB
最终致命：CUDA error: an illegal memory access was encountered
```

第一反应是 autotune 描述里的 `IS_DIVISIBLE=False` —— 统一 padding 的 16448 不是 128 的
倍数（16384+64，`inject_abot_text.py` 里 `align=64`），而 flex 的 sparse block 是 128。
怀疑 partial block 把 q 索引推到 16512，`ann[q]`/`frm[q]` 读越界。

**写了最小复现把两个假设分开，两个都被否掉：**

| 条件 | 结果 |
|---|---|
| seq_len=16448（非 128 倍数） | 前向反向都 OK |
| seq_len=16512（128 倍数） | 前向反向都 OK |
| 56 头真实尺寸 1x56x16448x128 | OK，best_time 56.5 ms |

那条共享内存 OOM 是**无害的** —— 它只废掉一个候选，autotune 跳过它继续。
真凶要回日志里对：7 张卡都正常选出 kernel（`best_time` 都是 56 ms 左右，和单卡复现
一致），**只有 rank2 的 `best_time` 是 `Infinity`** —— 6 个候选全灭。

`mode="max-autotune-no-cudagraphs"` 会在第一步实测 6 个前向 + 13 个反向候选。候选里有
跑得出 illegal memory access 的，而 IMA 会污染**整个 CUDA context**，不只是那一个候选。
表现就是 8 卡里随机一张在第 0 步挂掉。更麻烦的是失败结果会写进按 device 分键的磁盘
缓存：第二次跑 rank2 **仍然**死，但换了个死法（`NoValidChoicesError`，连
`Autotune Choices Stats` 都没打出来）—— 前一次的残留被读回来了。

修法不是调块大小，是**把 autotune 整个拆掉**。因为它一点收益都没有：

```
默认启发式配置    稳态 75.6 ms/iter
max-autotune     稳态 76.1 ms/iter      <- 反而略慢
```

赢家永远是默认那个配置（`BLOCK_M=128, BLOCK_N=64, num_warps=8`）。花 30 秒实测 19 个
候选，换来的是 0 收益 + 一个能让训练随机挂掉的雷。`attention.py` 去掉 `mode=` 即可。

> **两点教训**。一是**只有一个 rank 死的时候，先去看活着的 rank 打了什么** ——
> 7 张卡的 `best_time` 一致、和单卡复现也一致，这才把「配置本身跑不了」这个假设排除掉，
> 剩下的只能是过程性的污染。二是**日志里最刺眼的那条错误未必是死因**：
> 共享内存 OOM 又长又红又出现在每张卡上，但它是良性的；真正的死因 `best_time: Infinity`
> 是 JSON 里一个不起眼的字段。

### 一串小的

- **`pgrep -f` / `pkill -f` 自匹配**：模式串出现在自己的命令行里，等待循环死锁、
  `pkill` 把自己杀了。用 `"train[.]py"` 这种括号写法规避。
- **原子写的临时文件**：`ls *.mp4` 把 `.tmp.mp4` 数成产物，等待循环提前触发；
  两个进程写同一个 `gt.mp4` 时，固定的 `.tmp.mp4` 被先完成者 rename 走，
  后者 `os.replace` 报 FileNotFound。临时名加 pid。
- **float32 累加 80 亿个小数**：算 LoRA 有效权重 `W=B@A` 的范数，图省事把 104 个模块
  `cat` 成一个 8.02B 元素的向量再 `.norm()`。同一个文件，逐模块累加得 **13.25**，
  这么算出来是 **8.97** —— 每项都是 1e-9 量级，running sum 一大起来后面的项就被吃掉了。
  **它不报错，只是安静地少算 32%**，而且看着像个正常数字。逐模块累加 + float64。
  第一次算出的方向余弦 +0.0557 也是这么来的，真值是 +0.0245。
- **checkpoint 名的字典序**：盯训练的脚本用 `ls | tail -1` 取最新 checkpoint，结果
  `step-1000` 的**字典序排在 `step-500` 前面**，step-1000 落盘时一声不响。
  和前面 `ls *.mp4` 数进临时文件是同一类错误：拿文件名当有序数据用。改 `sort -n`。
- **JS 的暂时性死区**：可视化页里 `const KIDX` 声明在渲染代码之后 —— 函数声明会提升、
  `const` 不会，整个 script 抛 ReferenceError，页面一片空白。而"占位符已替换 /
  标签配平 / id 都存在"这类静态检查全是绿的。补了
  [`check_page_js.py`](../code/abot/check_page_js.py)：假 DOM 下真跑一遍 script。
- **判据自己漏报**：上面那个 `check_page_js.py` 的假 DOM 只有 `getElementById` 和
  `innerHTML`。新的核对台改用 `createElement` / `appendChild` 建树，检查器直接报
  `TypeError: document.createElement is not a function` —— **看着像页面坏了，其实是
  判据不够用**。补齐建树那套之后顺手加了一条：选择器要真的去匹配 `innerHTML`，
  匹配不上返回 `null`，让写错的选择器当场暴露（这类错误的线上表现是"某块区域空白"）。
  改完必须拿旧页回归一遍 —— 判据改了，它验过的结论就得重验。

## 七、贯穿始终的一条

这套方案**出错基本不会当场报警**，只会在训练里静默表现为"学不到绑定"。
所以每一层都配了判据，且判据本身也要验：

| 判据 | 抓什么 | 备注 |
|---|---|---|
| `probe_action_mask.py` | 掩码语义、padding、**掩码复用一致性** | 6 条，改 DiT 后必跑 |
| `verify_text_cache.py` | 缓存完整性、seq_len 唯一性 | 8 条，逐条核不抽查 |
| `analyze_probe.py` | 文本通道控不控运动 | 相位相关，符号已标定 |
| `check_page_js.py` | 可视化页的运行时错误 | 静态检查验不出来 |
| 标注核对台 | 标注跟 **GT** 对不对得上 | 验数据，统计量验不出来 |
| [推理结果核对台](action_prompt_text_viz.html) | **生成画面**跟标注对不对得上 | 验模型，肉眼判 |

`compare_action_ckpt.py`（权重差分）在零参数方案上**失效**了 —— 没有动作层可差分。
新判据应该是「只改第 k 条标注，测输出的哪些帧变了」：变化集中在第 k 帧及邻域即绑定
生效。注意 37×37 注意力对角占优在硬掩码下是**架构保证**的、恒为真，不能当判据。
这个工具还没写。

### 训练跑起来之后，能验什么、不能验什么

step-500 落盘后做了两件事，第二件差点被自己误读。

**能验的：模型在不在学。** LoRA 的 `lora_A` 是随机初始化的、天生非零，`lora_B` 从**零**
开始 —— 所以「整个 checkpoint 的全局 L2 非零」什么都说明不了，只有 `B` 的范数离开零
才是学习真的发生了。实测 104 个 `lora_B` 全部离零（L2 均值 1.23，最小 0.42），
52 个 block × `qkv_proj`/`out_proj` 一个不落，没有哪一层是死的。

**不能验的：绑定学没学到。** 有了两个 checkpoint，第一节那套权重差分看似能复活：

```
|W_500| = 13.25   |W_1000| = 24.26   |ΔW| = 20.00
ΔW 与已有 W 的方向余弦 = +0.0245        （加性 bias +0.064，FiLM 收敛到 +0.047）
```

余弦跟两次失败的数字撞在同一档，看着很吓人。但**这是个误读，两边差分的根本不是同一个
东西**。bias / FiLM 差的是一个专职编码动作的动作层，它的方向自相矛盾就等于动作学不进去；
这里差的是 52 层 `qkv_proj`/`out_proj` 上的通用 LoRA，它在做的是把base 模型适配到这个
数据集，**动作条件根本不走它** —— 整个文本注入方案的立足点就是条件通路零新增可训练参数。
拿它的方向余弦去判断"绑定学没学到"，是在测一个跟结论无关的量。

而且单个区间本来就说明不了什么：第一节能判死，靠的是**三个区间的趋势**（量级涨 3 倍而
余弦一路掉）。这里只有一个区间，且量级在健康增长，不是 bias 那种持续衰减：

```
step-500   |W_eff| = 13.25
step-1000  |W_eff| = 24.26   +83.1%
step-1500  |W_eff| = 29.75   +22.6%
```

> **教训**：一个判据失效之后，不要因为"手头正好有能算的量"就把它硬接回来。
> `compare_action_ckpt.py` 在这个方案上失效的原因没有变 —— 动作层不存在，
> 换个东西差分并不能让它重新有效。绑定这件事仍然只能等那个还没写的工具。

### 四件当时说不清、后来查清楚的事

**测试集干净，而且不只是"样本不重叠"。** 训练 7872 / 测试 128，交集 0。更强的一层：
三个 metadata 文件里 `window` 全是 0、`sample_id` 全唯一 —— **一个 sample_id 就是一条
episode**，所以不存在"同一条 60s 录像的不同窗口分散在两边"这种隐蔽泄漏。
`split_abot_metadata.py` 里有一句断言专门防它：`refusing an episode-leaking split`。
**代价是扩数据时会撞上**：用多窗口把数据翻倍，同一条 episode 的 w000 / w001 就会分到
两边，那时切分必须改成按 sample_id 分组，不能再按行 hash。

**续训能做，但不是断点续训。** `--lora_checkpoint` 可以接着已有权重训。但存档里只有
LoRA 权重（208 张量 / 131 MB），**没有优化器状态** —— Adam 的一阶二阶动量从零重建、
LR 调度重新开始。调度器是 `ConstantLR`，没有衰减曲线要接，所以影响有限；
真要严格续训得改保存逻辑。

**数据的天花板比预想高一个量级。** 源数据就挂在本机：
`ABot-World-Explorer-500h`，2.5 TB / **30969 episodes**。每条 60s/1800 帧，
每个窗口只吃 162 帧 —— 最多能切 11 个互不重叠的窗口，理论上限约 **34 万条**切片。
切片脚本的窗口编排本来就是为此设计的：所有 tier 都是同一个全局顺序的**前缀**，
扩量只能往后追加，绝不能重排前缀（实测跳过已有 16000 条只花 11 秒）。

**"换 action 出不出不同结果"当时还测不了。** 推理时 37 条文本是从片段自己的 npy
算出来的，没有覆盖入口。补了 `--action-preset`：因为文本是按键的纯函数，
替掉 `keys9` 之后整条链路无需再改。注意这只是**粗粒度**判据 ——
它回答"换 action 出不出不同且符合的结果"，回答不了"第 k 条标注绑不绑第 k 帧"。

一条命令跑完探针 → 数据构建 → 校验 → 起训：

```bash
bash code/scripts/run_text_pipeline.sh
```

每一步不过就停。
