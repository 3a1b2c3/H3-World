# 现在这个模型能不能生成更长的视频

> 一句话结论：**能。两条路都实测跑通了**，不用改架构、不用重训。
> 但两条路各有各的失败模式，真正干净的方案要改架构 + 重训。

> **实测已完成**（step-9840，同一条首帧）：一次生成 **10.1 秒**、分块续写 **15.5 秒**，
> 两条都没崩。结果与逐帧曲线见[长视频实测对照台](longvid_viz.html)。

现在的产出是 124 帧 / 24fps / **5.2 秒**。下面说清楚三件事：做不做得到、
架构支不支持、用什么方法。

---

## 一、先说结论

| 问题 | 答案 |
|---|---|
| 当前 checkpoint 能生成更长的吗 | **能**。有两条路不用重训 |
| 模型架构支持吗 | **支持**。帧数不是写死的，位置编码也没有硬上限 |
| 有没有代价 | **有**，而且两条路的代价完全不同（见第四节） |
| 有没有"干净"的方案 | 有，但要改注意力 + 重训，是最大的一块工程 |

---

## 二、为什么是 5.2 秒 —— 这个数字是哪来的

不是模型的上限，是**我们自己选的切片长度**。

```
latent_t = ((num_frames - 5) // 17) * 5 + 2
124 帧 -> latent_t 37
```

模型把视频压成 `latent_t` 个"潜在帧"，每 5 个潜在帧覆盖 17 个真实帧
（分组是 1,4,4,4,4 帧，不均匀）。所以**帧数必须是 `17k + 5`**：

```
124 帧 = 5.2s    192 帧 = 8.0s    243 帧 = 10.1s
362 帧 = 15.1s   481 帧 = 20.0s   719 帧 = 30.0s
```

124 是 H3 官方所有 example 用的值，我们跟着用了。**训练集里全部是 124 帧**，
这一点很重要，第四节会回到它。

---

## 三、架构支不支持 —— 三处都查过了

**① 帧数是个参数，不是常量。**
生成管线的签名里 `num_frames: int = 124` 就是个普通入参，注释还写明会自动
向上对齐到最近的 `17n+5`。改成 243 或 481 是合法调用。

**② 位置编码没有长度上限。**
RoPE 用的是连续函数 `1/10000^(i/d)`，位置多大都算得出来，不存在"查表查不到"
的问题。但**算得出来不等于算得准** —— 见第四节。

**③ 注意力是全连接的，不受长度限制。**
当前是双向全连接（`_sdpa_varlen_attention`），任意两个 token 互相可见。
它不像因果模型那样有"只能往前看"的结构约束，长度上是自由的。

**④ 首帧条件可以喂任意图片。**
这是最关键的一条。推理时首帧是这样传的：

```python
keyframes=[frames[0]], keyframe_indices=[0]
```

`keyframes` 收的是普通的 PIL 图片列表，`keyframe_indices` 指定塞在第几帧。
**这意味着"拿上一段的最后一帧当下一段的首帧"是现成能力，一行都不用改。**

---

## 四、两条今天就能走的路

### 路一：直接把 num_frames 调大（一次生成一整段长的）

**怎么做**：推理时把 `num_frames` 从 124 改成 243 / 481。动作文本也跟着变多
（37 条变成 72 条 / 142 条），规则表是纯函数，自动就能生成。

**好处**：整段一次生成，**没有接缝**，时间上完全连贯。

**代价有两条，第二条是真问题**：

*代价 A —— 慢，而且是平方地慢。* 注意力的计算量是序列长度的平方。
显存倒是线性的（flash/flex 注意力不物化 n×n 矩阵），所以卡放得下：

| 时长 | seq_len | 激活显存 | 计算量 | 单卡推理耗时（推算） |
|---|---:|---:|---:|---:|
| 5.2s（现在） | 16,193 | 1.0x | 1.0x | 8 分钟 |
| 10.1s | 30,088 | 1.9x | 3.5x | 28 分钟 |
| 20.0s | 57,878 | 3.6x | 12.8x | 102 分钟 |
| 30.0s | 85,668 | 5.3x | 28.0x | 224 分钟 |

*代价 B —— 训练分布外。* 模型只见过 37 个潜在帧的序列，一次都没见过更长的。
让它生成 72 个，RoPE 的时间位置要外推到训练时从未出现过的范围。

**这里我预测错了。** 我原本写的是"典型表现是后半段质量塌掉"。实测 10.1 秒（243 帧）：

```
逐帧变化量四分段均值   3.80 → 3.52 → 4.42 → 4.20     后半段运动量反而更高，没有塌
变异系数 std/mean      0.944                          但忽快忽慢，很不稳
异常尖峰               第 89 帧 9x 均值、第 118 帧 7x  中间有几处硬切
```

**没塌，但会硬切。**真正的问题不是"越往后越糊"，而是整段忽快忽慢、
中途插进几帧数倍于均值的突变。这是一个和预期完全不同的失败模式 ——
如果只按"后半段崩不崩"去看，会误判成"通过"。

### 路二：分块续写（一段接一段）

**怎么做**：生成第一段 5.2 秒 → 取它的最后一帧 → 当作第二段的首帧再生成
5.2 秒 → 接着取末帧…… 拼起来。动作文本每段各给各的，所以**按键控制照样有效**。

**好处**：
- 每一段都在训练分布内（永远是 124 帧），质量不会因为变长而塌
- 时长**没有上限**，想要多长接多长
- 耗时线性增长，不是平方（每段固定 8 分钟）
- 代码几乎不用改 —— `keyframes` 本来就收任意图片

**代价，三条**（第 1 条已实测）：

1. **接缝**。两段之间只靠一帧图片衔接，运动的速度和方向是断的。
   实测 3 段 × 124 帧：**接缝处的逐帧变化量只有邻域的 0.46 倍**（两处都是）。
   注意方向 —— 接缝不是"跳变"而是**低谷**：下一段的首帧就是上一段的尾帧，
   两帧近乎重复，所以看上去是"动作卡了一下"，不是画面跳一下。
   这正是"只传了一帧、传不了运动状态"的直接后果。
2. **误差累积**。第二段的首帧是生成出来的（不是真实照片），带着第一段的瑕疵；
   第三段又基于第二段…… 几段之后画面可能"跑偏"。
3. **只传了一帧的信息**。一张静止图片说不出"刚才在往哪动"，模型只能重新猜。

**能缓解，但不能根治**：
- 用 `keyframe_indices` 一次塞**多帧**历史（不只是末帧），把运动信息也带过去
- 相邻段重叠几帧再做交叉淡化，藏住接缝
- 用负 prompt + CFG 让动作服从度更强，减少段间抖动

## 五、真正干净的方案（要改架构 + 重训）

**块因果注意力 + KV cache**，也就是让模型真的能"续写"而不是"重启"。

**思路**：把序列切成块，块内双向、块间只能往前看。生成第 N 块时，前面所有块的
KV 都在 cache 里，模型看得见完整历史，而不是只看见一张图。这样既没有接缝，
也没有长度上限，而且因为不用重算历史，速度还快。

**改动量最大，有三处硬骨头**：

1. **注意力要从双向改成块因果**。当前 `_sdpa_varlen_attention` 是全连接。
2. **RoPE 时间轴要重新推导**。时间轴是**非均匀**的（每 5 个潜在帧覆盖 1,4,4,4,4 帧），
   因果化之后位置怎么排不是照搬就行。
3. **必须重训**。改了注意力结构，现在这个 checkpoint 直接作废。

配套还需要**少步蒸馏**（把 50 步降到 4–8 步），否则实时交互谈不上 ——
但那是"快"的问题，不是"长"的问题，别混在一起。

## 六、建议的顺序

| 步骤 | 做什么 | 状态 | 结论 |
|---|---|---|---|
| **1** | 路一实测：`num_frames=243` 生成 10 秒 | ✅ 完成 | 没塌，但变异系数 0.944、有硬切 |
| **2** | 路二实测：分块续 3 段拼成 15.5 秒 | ✅ 完成 | 平稳（0.463），但接缝处动作卡顿 |
| **3** | 挑一条做扎实 | 待定 | 见下 |
| **4** | 真要做实时交互，再上块因果 + KV cache + 蒸馏 | 未开始 | — |

**目前看路二更值得做扎实**：它整体平稳得多（变异系数 0.463 vs 0.944），
长度无上限，耗时线性；唯一的缺陷是接缝，而接缝有明确的缓解方向 ——
用 `keyframe_indices` 一次塞**多帧**历史，把运动状态也带过去，而不是只给一张静止图。
路一那种"中途硬切"反而更难对付，因为它没有一个明确的着力点。

**挤卡推理实测可行**：单条 10 秒推理只额外占 **14.8 GB**（`--vram-limit-gib 30`），
每卡还剩 59 GB 空闲。代价是训练从 9.48 s/it 掉到 14.32 s/it（+51%），
推理进程一退出立刻恢复，不留痕迹。

---

## 七、一句话总结每条路

| 方案 | 要重训吗 | 时长上限 | 实测表现 |
|---|---|---|---|
| 调大 `num_frames` | 不用 | 受算力限制 | **没塌，但忽快忽慢 + 中途硬切**（cv 0.944） |
| 分块续写 | 不用 | 无上限 | **平稳**（cv 0.463），**接缝处动作卡顿**（0.46×） |
| 块因果 + KV cache | **要** | 无上限 | 未做。工程量大，当前 checkpoint 作废 |

> **一条方法论上的收获。**我原本预测路一会"后半段塌掉"，实测没塌 ——
> 但它有另一种失败（硬切），而且如果只盯着"后半段崩不崩"这一个指标，
> 会把它误判成通过。**预测失败模式比预测成败更容易错**，
> 所以判据要量的是"时间上连不连续"这种可观测量，而不是预设的某种崩法。
