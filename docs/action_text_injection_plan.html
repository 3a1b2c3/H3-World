MiniMax-H3 · ABot 动作条件微调 · 方案定稿

逐 latent 动作文本注入

加性 bias 与 FiLM 两种特征空间注入都已实测失效。这一版把动作换成 每个 latent 一条结构化文本条件，走 H3 预训练过的文本通路， 条件通路零新增可训练参数。先在双向模型上验证信号， 但每一处设计都按将来转流式的约束来定。

101 种全数据集标注词表
+3.3%注意力开销
0条件通路新增参数
3 处核心代码改动

为什么是这个方案

两条独立的证据指向同一个方向。

方案注入点调制量级ΔW·W 余弦结论
加性 biasblock 入口0.107% @2952 +0.064失效
FiLMAdaLN 之后0.33% @3000 +0.047失效

一、我们自己的诊断。FiLM 修好了加性 bias 的表达能力缺陷（调制随内容变化）， 量级也涨了 3 倍，但方向余弦反而从 +0.064 掉到 +0.047。逐段看 |scale| 是 0.183→0.233→0.267→0.297→0.330%，增速持续收窄。 换机制没用，说明问题不在"乘性还是加性"，而在信号本身。

二、Incantation 的消融。它的 Action-Index 基线正是我们跑过的方案 —— 把动作表示成联合词表上的 one-hot，过一个可学习投影层。对比自然语言接口：

自然语言Action-Index（= 我们的方案）
跨实体动作迁移89%43%
词表外动作90%0%

要说公道话：这两个指标测的是泛化，不能直接推出"one-hot 连基本控制都做不到"。 但方向和我们的诊断一致 —— 离散索引没有组合语义。

而 H3 的文本通路正好是现成的、预训练过的、且当前完全空着的。 序列布局是 [text | cond | audio | video | pad] —— 文本本来就是同一条 self-attention 序列里的一段 token，H3 没有 cross-attention 不是因为它不能接外部条件， 是因为它用拼接解决了。

更关键的是：现有训练 prompt 是 1002 字符的纯静态场景描述（地形、植被、角色穿什么）， 一个运动词都没有。微调时模型面对的是「静态描述 + 0.1% 强度的动作信号 → 有运动的视频」， 运动在条件里几乎没有对应物，学边缘分布就是它的最优解。这本身就是梯度互相抵消的一个合理机制。

信号设计：标注写什么

三元组模板，逐条独立编码

# 全局锚点，1 条（8 tok）
A third-person view of a man.

# 逐 latent，37 条，固定句式只换槽内容（合计 416 tok，实测 296–511）
the man walks forward and strafes left, camera holds steady
the man stands still,                   camera pans left slowly
the man walks backward and strafes right, camera pans right sharply
the man strafes right,                  camera pans left slowly and tilts up
        └── 怎么动 ──┘                          └── 相机视角怎么动 ──┘

# 阈值来自 7872 训练集 600 条 clip 的池化后实测分位
d_yaw:  |v| < 0.10 不写 · 0.10–0.90 slowly · ≥ 0.90 sharply   # yaw>0 = 左（J）
d_pitch:|v| ≥ 0.20 才写 tilts up / down

主体锚点单独一条，让「the man」有指代物；首帧还通过 <Picture 1> 的 358 个视觉 token 进来，场景信息是冗余的，长场景描述砍掉。

实测词表只有 101 种。400 条 clip × 37 步 = 14800 条标注， 去重后 101 种，单条 clip 内平均只有 5.3 种。这意味着整个数据集只需 ~101 次文本编码， 一次算完缓存即可 —— stage-1 文本缓存的重建几乎是免费的，不必跑 7872 次编码器。 覆盖度：58% 的步有相机运动，59% 有移动，仅 11% 完全静止。

「相机怎么动」必须用 COLMAP 实测的 6 个通道生成，不能用 IJKL 按键。 这是整个方案唯一能真正跳出上一轮死结的地方。

如果三个从句全部由同样 8 个 bit 推出，那不管注入得多漂亮，信息量一个比特都没多， 只是把 one-hot 换成了英文 —— 那正是 Action-Index 基线在做的事。而 npy 里的 d_pitch/d_yaw/d_roll/d_x/d_y/d_z 是从画面反推的实际运动，稠密（33/37 非零）、 连续、几何意义明确，量化成程度副词后携带的信息真正超过了 8 bit。

关于 cam_valid：实测后风险比预估的小。抽查 600 条 clip， npy 里相机块整段全零的比例是 0/600 —— cam-dropout 发生在注入阶段而不是数据里， 磁盘上的标注是干净的。所以文本管线只要不套用 dropout，规则表直接从 npy 读就是对的。 第 18 维 cam_valid 仍建议补上（防止将来别处误用），但不再是本方案的阻塞项。 规则表已留好降级路径：cam_valid=False 的步自动退回 IJKL 按键生成相机从句， 代价是那些步的信息量退回 8 bit。

编码方式：逐条独立 + 去重字典

不做整段上下文编码。同一句标注永远得到同一个嵌入，本质是一张预训练语义查找表。 这既给了前两次缺的一致性，也是流式的硬约束 —— 推理时未来动作未知，没法一次性编码整段。 Incantation 的实现正是如此：

# incantation/inference.py
unique_prompts = list(dict.fromkeys(prompts[:num_gen_frames]))   # 去重
embeds = [prompt_to_embed[prompts[fi]] for fi in range(num_gen_frames)]

动作序列 → 标注串走手写规则表（确定、可复现、零成本），不过 VLM。

注入设计：序列布局与绑定

为什么用镜像偏移，而不是把标注放到帧的 t 上

视频的 t 轴原点就是 text_len（_video_grid(latent_t, frame, float(text_len))）， 所以"放到帧的 t 上"按定义会越过 text_len。而预训练里文本与视频的 t 偏移恒为负， 越过去意味着偏移出现零和正值 —— 这是模型没见过的配置，且它落在低频带里（高频档在几百的跨度上早已混叠）。

镜像偏移把绑定信号从"零距离"换成"恒定 −200"，模型要学的规则是"往回看 200"， 一条统一规则，而不变量不破。实现细节：取 A = text_len − 200 会让最后一条标注与首帧 cond 撞在同一个 t 上，硬掩码下无害，但建议退一格（text_len = 782 时取 A = 581）避免歧义。

硬掩码切断跨帧上下文的顾虑，H3 已经替我们解决了。 文本行在被 scatter 进主序列之前，先过了 2 层 token_refiner 的全连接自注意力 （refiner_cu = [0, text_len, text_len]）。37 条标注彼此、以及和主体锚点之间已经充分混合过。 主干里的掩码只切断"标注→别的帧的画面"，不切断"标注→别的标注"。动作惯性的上下文是白拿的。

CFG：把负 prompt 做成"动作零参考"

文本参与 CFG，而 action_cond 不参与（design_doc §6.1 记的遗留问题）。 动作一旦走文本，cfg_scale 就直接变成动作服从度的放大器。

正 prompt = 主体锚点 + 37 条动作标注
负 prompt = 主体锚点 + 37 条 "the man stands still, camera holds steady"
训练时对动作脚本做随机 dropout，CFG 才站得住

这样放大的恰好是动作那部分的差量，而不是笼统的 prompt 服从度。 顺带：infer_abot.py 从没传过 cfg_scale，pipeline 默认 1.0 —— 这个旋钮至今没开过。

流式约束：哪些选择是为将来定的

两条会挡路的选择，必须现在就定对。

一、编码方式必须是逐条独立，不能整段上下文编码。 流式推理时未来动作未知，没法一次性编码整段。

二、不能用 <X.X seconds> 绝对时间戳。 滑动窗口下时间无界增长，<127.3 seconds> 这种东西训练里根本没见过。 绑定改由位置 + 掩码承担，标注文本里不出现时间。

验证阶梯

  1. 第 0 步 · 十几分钟 · 零训练
    零训练探针：H3 的文本通道到底控不控运动

    拿基座模型（不加任何 LoRA），同首帧同 seed，只改 prompt 尾部： 加运动语言 vs 反向运动语言 vs 不加，同时把 cfg_scale 从 1.0 拉到 5 测一档。 这是整个方案的红灯/绿灯 —— 三条视频若几乎一样，文本通道是死的， 该回头看「相机即位置编码」那条路（PRoPE 一族，每 head 有 62/128 通道空着）。

  2. 第 1 步 · 半天
    规则表 + score_mod 透传 + packing 改造

    落点探针的判据：去掉标注行时与原模型逐位等价、 掩码只作用于"标注 × 非本帧 video"这一块、 第 k 条标注的行区间确实对上第 k 帧。这三条和现有探针同构。

  3. 第 2 步 · 数百步
    换判据：单条标注扰动定位

    compare_action_ckpt.py 靠差分动作层权重工作， 在零参数方案上直接失效，没有动作层可差分。新判据： 只改第 k 条标注，测输出的哪些帧变了。 变化集中在第 k 帧及邻域 = 绑定生效且局部；全帧齐变或全帧不变 = 有问题。 几十步就能跑，不用等收敛。

    注意：37×37 注意力对角占优在硬掩码下是架构保证的，恒为真，不能当判据。

  4. 第 3 步
    正式训练 + A/B 对照

    同首帧同 seed，一次真实标注、一次全 "stands still" 标注。 两条视频若几乎逐帧一致，说明动作仍未起作用；有明显分叉才算控制住了。

  5. 与训练并行 · 不占 GPU
    训按键 → 相机增量的映射

    推理时用户只给按键，相机从句得由映射产生。实测相机通道能以 AUC 0.88–0.99 反向预测按键，说明正向也该可学。流式阶段这一步从"可选"变成实时必需。

  6. 下一阶段 · 周级
    转流式

    块因果掩码（复用 score_mod）→ KV cache（新建）→ 少步蒸馏。 并决定音频是一起流式化还是先关掉。5 天内做不到端到端流式， 这几天的现实目标是把"动作可控"坐实。

风险与未知

一、把 8 个 bit 换成英文单词，本身不增加任何信息量。 唯一的真实增量有两个：Qwen3-VL 带进来的视觉语义先验（它知道 "turn left" 长什么样）， 以及 COLMAP 相机通道（这个是我们数据里真实多出来的信息）。 方案的成败基本押在这两条上 —— 所以相机从句用实测通道不是优化项，是必要条件。

二、位置绑定仍有 OOD。镜像偏移保住了"文本在视频之前"的不变量， 但标注块内部的 token 间距变成 1.667/6.667 而不是 1.0，这个配置没见过。 硬掩码是主力绑定，位置是第二条通道，这样安排就是为了让位置那条失效时方案不塌。

三、容量差距。Incantation 是 16×H100 全参微调，我们是 LoRA rank 32。 缓解在于掩码把"学绑定"这件事从模型身上拿掉了，但差距真实存在。

四、H3 是音视频联合模型。序列里始终有 414 行 audio， 这是所有参考工作都没有的复杂度，流式化时会集中暴露。
