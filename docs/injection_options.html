动作注入方案选型

加性 bias 和 FiLM 两种特征空间注入都已实测失效 —— 同一个失效签名： 调制量级涨不上去，梯度方向余弦一路下滑。这页把能查到的注入方式按可行度从高到低排开， 最上面那一族是这次调研新补的：把相机位姿折进 RoPE，作用在 attention 内部，零新增参数。

两次失败给出的信息

不是"再多训一会儿"的问题。两种机制不同的注入方式给出了同一个签名，这本身是有信息量的。

方案注入点调制量级ΔW·W 余弦实际/理论步长结论
加性 bias① block 入口 0.107% @2952 +0.0641.92% 失效
FiLM② AdaLN 之后 0.33% @3000 +0.0471.16% 失效

FiLM 的量级确实比 bias 高了 3 倍，但方向一致性反而更差。逐段看 500→3000 的 |scale|：0.183% → 0.233% → 0.267% → 0.297% → 0.330%，增速持续收窄； 同期余弦 +0.122 → +0.116 → +0.093 → +0.079 → +0.047，已经低于 bias 基线。 按这个斜率外推到 9840 步只能到 0.7% 左右，进不了 1%–5% 的有效区间。

这说明问题不在"乘性还是加性"。FiLM 修好了原先诊断出的表达能力缺陷 —— 调制随内容变化，理论上不该再抵消 —— 但抵消照旧。剩下的解释只有一个方向： 8 维按键本身没有携带足够信息去解释画面该怎么变，所以不同样本仍在要求相互矛盾的更新。

为什么第一组在 H3 上真的装得下

这不是纸面推导 —— 我把 H3 的 RoPE 配置按实际张量尺寸算了一遍。

H3 每个 head 的 128 个通道，实际只用掉一半

H3 的配置是 attention_head_dim=128、rope_inv_freq_len=16、三个位置轴 (t,h,w)。于是 _apply_rope 旋转的维度是 2×(3×16)=96， 剩下 32 个通道原样穿过，完全不带位置信息。再算已旋转的 96 维里有多少是"活的"：

按本片段的实际跨度算 （latent_t=37，fr=390=15×26 → t 轴 0–36、h 轴 0–14、w 轴 0–25）： 逆频率最低的那几档在整段跨度内相位只扫过 0.006–0.05 rad， 数值上等同于常数 —— t 轴 4/16 档、h 轴 6/16 档、w 轴 5/16 档都属此列。

结论：每个 head 有 62/128 个通道不携带任何位置信息（32 直通 + 约 30 死带宽）， 接近一半的通道预算是空的。ReRoPE 说的"RoPE 没用满自己的频谱带宽"，在 H3 上不只是成立， 而且余量比一般模型更大 —— 因为 16 档逆频率要分给三个轴，而我们的片段每个轴都很短。

复现命令在 docs/action_injection_design.md；一行 torch 即可验： 1/(10000**(torch.arange(16)/16)) * 36 看 t 轴各档的总相位。

推荐方案

把相机位姿折进 RoPE，落在 attention 内部

# MiniMaxH3Attention.forward —— 唯一需要改的地方
q = self.q_norm(q); k = self.k_norm(k)
if rope_freqs is not None:
    q = _apply_rope(q, rope_freqs)          # 原有时空 RoPE，96 维
    k = _apply_rope(k, rope_freqs)

if cam_P is not None:                        # 新增：相机几何，作用在直通的 32 维上
    q = _apply_cam(q, cam_P,     start=96)   # q ← P·q
    k = _apply_cam(k, cam_P_inv, start=96)   # k ← P⁻ᵀ·k

out = _sdpa_varlen_attention(q, k, v, cu_seqlens=cu_seqlens, ...)

四条理由，都对应已核实的架构事实： ① rope_freqs 在 forward 里只算一次就传给全部 50 层， 所以这是一处改动、全模型生效； ② 用的是 96 之后的直通通道，预训练的时空 RoPE 一位不动； ③ 零新增可训练参数 —— 前两次失效的病灶（动作层权重的梯度互相抵消）在这条路上根本不存在； ④ 相机位姿为零时 P=I，与原模型逐位等价，现有落点探针的判据继续成立。

先用 ViewRope 变体落地，而不是 Warped PRoPE。两者思路同源，但工程量差一截： ViewRope 只旋转 q/k，改动完全关在 _apply_rope 里； Warped PRoPE 还要给 v 乘 P⁻¹，得动 MiniMaxH3Attention.forward 和 varlen attention 的调用路径。先用只动 q/k 的版本验证机制活不活，活了再考虑要不要上完整投影。

三条必须先解决的前置问题，别跳过。

一、我们的相机通道是增量，PRoPE 要的是绝对位姿。 d_pitch/d_yaw/d_roll/d_x/d_y/d_z 得逐帧累积成 world-to-camera 矩阵 W， COLMAP 的尺度不确定性会在累积中放大 —— 必须做平移归一化（ReRoPE 实测这一步显著改善画质）。

二、cam-dropout 的 62.5% 错标会重新咬人。置零 ≠ 缺失，零向量在几何上就是"相机静止"， 而 64 条冒烟里被置零的 40 条运动 |max| 中位 1.83，没有一条接近静止。 走这条路必须先加第 18 维 cam_valid 标志位。

三、PRoPE 家族的原始场景是静态场景多视角，我们不是。 它编码的是相机之间的几何关系，对场景本身的动态（角色移动、NPC、天气）不置一词。 第三人称游戏里 COLMAP 反推的位姿本身也更脏。这条路能不能吃下游戏视频，是真实的未知数。

另一个维度：注入什么，可能比怎么注入更重要

两次失效之后，这条从"可能"升级成了"多半是主因"。

两条路在这里合流了。PRoPE 一族要的输入就是相机投影矩阵 —— 也就是说， "换信号"不再是 FiLM 之后的备胎，而是第一组方案的前置条件。 数据侧我们已经有一半：切片 npy 是 17 维，8 个按键之外还有 6 个 COLMAP 反推的相机通道， 稠密（33/37 token 非零）、连续、几何意义明确。

推理时相机增量不可得这个老问题，解法照旧是 GameCraft 那条：训练时用相机表示做条件， 另训一个按键 → 相机增量的轻量映射，推理时用户给按键、映射出相机、再喂给 DiT。 实测相机通道能以 AUC 0.88–0.99 反向预测按键，说明这个映射强相关、可学。

下一步计划

  1. 立刻
    停掉 FiLM 训练

    step-3000 的诊断已经判死：余弦 +0.047 低于 bias 基线，量级增速持续收窄。 剩下的 6485 步按斜率外推只能到 0.7%，进不了有效区间。留着 checkpoint 做对照即可。

  2. 数据侧 · 不占 GPU
    把相机增量累积成绝对位姿，并补 cam_valid

    逐帧累积出 world-to-camera 矩阵，做平移归一化压掉 COLMAP 尺度漂移； 同时加第 18 维标志位区分"相机静止"与"相机缺失" —— 现在 62.5% 的样本贴的是错标签， 走几何路线这个错误会直接变成假的位姿监督。

  3. 改造 · 约半天
    先落 ViewRope 变体：只旋转 q/k 的直通 32 维

    改动关在 _apply_rope 内部。落点探针要重写判据： 位姿为零时与原模型逐位等价、anchor/text token 拿单位阵、 第 k 个 latent 步用的是第 k 帧的位姿。这三条和现有探针同构，改起来不难。

  4. 关键差异 · 必须先想清楚
    换掉验收判据 —— 旧的诊断工具在这条路上失效

    compare_action_ckpt.py 靠差分动作层权重工作， 而 PRoPE 一族零新增参数，没有动作层可差分。新判据应该是： 同首帧同 seed 下真实位姿 vs 单位阵位姿的 A/B 分叉幅度， 再配 self-attn 的 LoRA 权重漂移。这个工具要新写，别等训练跑起来才发现没法判。

  5. 与训练并行
    训按键 → 相机增量的映射

    推理时用户只给按键，位姿得由映射产生。AUC 0.88–0.99 的反向可分性说明正向也该可学。 这一步不依赖 DiT，可以完全并行做掉。

  6. 机制确认后
    叠加 AC3D 的限层与低频调度

    只往前若干层注入、只在去噪早期注入。这是正交增强，等主路径验活了再叠， 不要一次改两件事导致归因不清。

一个诚实的边界。第一组方法绕开了我们两次踩到的梯度问题 —— 因为它压根不引入参数 —— 但它换来了一个新赌注：相机几何是否足以解释这些游戏片段里画面的变化。 PRoPE 一族出身于静态场景的多视角合成，我们是第三人称、有角色和动态世界的游戏录像。 它能不能吃下这类数据，参考文献里没有直接答案。所以第 4 步（先把判据做出来）比改模型更重要 —— 这次要做到几百步内就能判死活，而不是又花 26 小时确认一遍。
